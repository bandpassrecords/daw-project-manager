# CLAUDE.md — DAW Project Manager

Instructions for AI assistants working on this codebase.

---

## Non-negotiables

### Tests are part of every task
- Every bug fix must include a regression test that would have caught the bug.
- Every new feature must include tests covering its logic in full.
- Run `flutter test` before every commit — only commit if all tests pass.
- CI runs the **whole** suite on Linux, Windows and macOS (the `unit_tests` matrix in `release.yml`), and every build and release job waits for all three. A push to `main` builds every app too, as a check (`COMPILE_ONLY`: no signing, notarizing or uploads), so two PRs merged in a row, or a commit pushed straight to main, are built together before a release finds out; a newer push cancels the older run, and pushes touching only `*.md`, `docs/` or `.claude/` skip CI. Write tests that hold on each: build expected paths with `package:path` (`p.normalize`, `p.join`), never POSIX literals — six archive/move tests once failed on every Windows run because CI only ran on Linux.
- If logic is too deep in the widget tree to unit test, write the closest possible test (model/service/repository level) and note explicitly what cannot be automated.
- **Real projects are the test of a reader.** `test/fixtures/projects/<daw>/<name>/` holds real projects (one, or one song's versions), each read and compared with its `.expected.json` by `project_corpus_test.dart`; `test/fixtures/midi/` does the same for `.mid` imports. Add one with `scripts/add_test_fixture.ps1` (`-Versions` for a folder of versions, `-MaxFileMB` to leave big audio out), record it with `UPDATE_FIXTURES=1`, and read the diff — a snapshot records bugs as faithfully as features (FL 7's 2-billion-tick clips once were one). No commercial audio or third-party MIDI transcriptions.
- **`test/flows/` runs whole features over copies of that collection** — scan, deep scan, MIDI to `.mid`, stacks, archive, sample pack, backup, profile moves — on a real database in a temp folder, through `FlowLibrary`. No window, so they run in the ordinary suite on every platform. A flow never reads the machine outside its temp folder: the projects name paths that exist only where they were made (see `_referencesWithin` in the sample pack flow). Anything a flow can't drive past — a file dialog — is a sign the work should be split from the dialog, as `BackupService.buildBackupJson`/`importBackupJson` were.

### Always use AppLocalizations for UI strings
- Never hardcode user-visible text in widget trees.
- Any label, tooltip, snackbar message, dialog text, or button label must have a key in `lib/l10n/app_en.arb` and be referenced via `AppLocalizations.of(context)!.someKey`.
- Add the key to all locale ARB files, then run `flutter gen-l10n`.
- The app ships in 9 languages — hardcoded strings silently break all non-English users.
- `app_pt.arb` is Brazilian Portuguese only — there is a single Portuguese locale for this app, and it targets Brazil. Never introduce European Portuguese spelling or vocabulary (e.g. "ficheiro", "deteção"/"detetar", "descarregar", "ecrã", "utilizador", "está a fazer"-style progressive) — use the Brazilian equivalent instead (e.g. "arquivo", "detecção"/"detectar", "baixar", "tela", "usuário", "está fazendo"). When adding or editing a `pt` string, match the vocabulary already established in the rest of `app_pt.arb`.

### New model fields must be evaluated for Drive sync AND local backup
- When adding a field to `MusicProject` (or any synced model), decide: is this user-generated data or a device-local preference?
- **User data** (metadata, timers, todos, paths) → add to `_serializeProject` AND `_deserializeProject` in `lib/services/google_drive_sync_service.dart`. If skipped, the field is silently lost on every Drive restore.
- **Device-local settings** (which theme is selected, layout, update checks) → do NOT sync. `AppSettings` fields are generally device-local.
- The split can run through one feature: a **custom theme's definition** is user data (synced and backed up), while **which theme is selected** is a device-local preference (neither). Ask the question per field, not per feature.
- Also check `lib/services/backup_service.dart` (local file export/import) for the same question, for any *global* (non-per-profile) data — `TodoTemplate`, `ProjectTemplate`, `TemplateRoot`, custom mixdown folder names, custom themes, phase settings. This is Flatpak's only backup path (see below), so a field skipped here is a field Flatpak users can never back up at all, not just "won't survive a Drive restore."
- Merging is **union, never deletion**: something present locally but absent in the incoming data is something made since, not something removed. On a same-id collision the newer `updatedAt` wins. `mergeCustomThemes` is the reference implementation.

### Google Drive sync is not offered inside Flatpak
- `GoogleDriveSyncService.isSupported` is `false` only when actually running inside a Flatpak sandbox (detected via the `/.flatpak-info` marker file every Flatpak app has at runtime), `true` everywhere else — including the plain Linux tarball and the AppImage. Every UI entry point to `GoogleDriveSyncPage` (dashboard, profile page, startup dialog, tray menu) is gated on it — don't add a new one without the same gate.
- Why: the desktop OAuth flow requires a client secret (confirmed against a live Google sign-in attempt — PKCE alone isn't accepted for this app's "Desktop app" OAuth client type; see the long comment on `_desktopClientSecret` in `google_drive_sync_service.dart`). Flathub's build sandbox has no secret-injection mechanism, so shipping the secret there would mean committing it in the open in the public Flathub submission repo. Not offering the feature was chosen over that for Flatpak specifically — the tarball/AppImage are built by this repo's own CI (`build_linux` in `release.yml`), same trust boundary as Windows/macOS, so they get the real secret too.
- The Flatpak build compiles `lib/config/oauth_config.dart` from the committed template's placeholder text directly (no real values, no GitHub secrets involved) — see `flatpak/README.md`. The Linux tarball/AppImage build (`build_linux`) injects real values from GitHub secrets like every other desktop platform.

### Deleting a project goes to "Recently deleted"
- Every deletion of projects — Delete… in the project menu, Delete Missing, removing a scan folder, excluding a path — goes through `ProjectRepository._trashAndDelete`: the whole row and its MIDI clips are kept in the profile's `ProjectTrash` for 30 days (Settings > Project folders), then removed, then tombstoned. A new way of deleting projects must go through it too. `restoreFromTrash` puts a row back with a fresh `updatedAt`, so it beats its own tombstone on every device, and replaces an empty row a scan added at the same path meanwhile.
- The trash is device-local (neither Drive sync nor local backup); the deletion and the restore sync as ordinary changes.
- Deleting a project whose file sits inside one of the profile's scan folders offers to exclude its path (`pathAScanWouldFind`: its folder when dedicated to it, else the file), or the next scan adds it back as a new, empty project.

### A profile is an artist: a song lives in one, and moves between them
- Profiles are separate artist names (solo, collaborations). A song belongs to exactly one; there are no shared projects. A folder scanned by two profiles gives each its own independent copy of every project in it, so adding one warns first (`findRootOverlaps` / `confirmScanFolderOverlap`, at every place that adds a scan folder) — a new place must call it too.
- "Move to profile…" (`planProfileMove` + `moveSongToProfile`, `lib/services/profile_move_service.dart`) moves a **whole song**: a version takes its stack and every other version with it. Same ids, notes, to-dos, events, MIDI clips; off the old profile's releases; tombstoned for the old profile only, new changes in the new one, so other devices follow. Files stay (their path is then excluded in the old profile, never a scan folder itself) or move into the target's folder — files before rows, checked copy before any delete (`firstCopyMismatch`). A move is not a deletion: nothing goes to the trash. Refused: archived songs, a target holding the song with details of its own, moving files of a hand-made stack spread over several folders.
- Settings > Project folders edits **any** profile's folders, excluded folders and Recently deleted (its profile picker; the cards below those are the same for every profile). It goes through `repositoryForProfileProvider(id)` and the `…ForProfileProvider` families, which hand back the active profile's own repository when `id` is the active one — never `repositoryProvider` there, or a change meant for another artist lands on the active one. Riverpod 3 pauses an unlistened provider, so a test reading these must listen first.

### Drive sync: one service, one way to back up, deletions that travel
- **One instance**: `GoogleDriveSyncService.shared` (also `googleDriveSyncServiceProvider`) is used by the sync page, the tray, the automatic timer and the project menu. Separate instances each held their own sign-in — the timer never saw a phone's, so automatic sync never ran there. Never `GoogleDriveSyncService()` in app code, and never `dispose()` it from a page.
- **Every "back up" is merge-then-upload** (`syncDatabase`), reached through `driveSyncStatusProvider.notifier.syncNow()` / `track()`, which run it under `exclusive` (one operation at a time) and report it: the dashboard's cloud button, the tray's status line and the sync page all read `DriveSyncStatus`. A plain `uploadDatabase` replaces Drive's copy wholesale — it is only the explicit "Replace Drive's copy" action. The tray's old "Backup now" called it and wiped other devices' changes.
- **Reading the backup marks nothing as merged.** Only `markMerged` (after a merge) or an upload records Drive's `modifiedTime` as seen; `isRemoteNewer` compares Drive's clock with Drive's clock. The upload reads the backup for its media hashes, and a restore can be cancelled after downloading — either used to hide "newer on Drive".
- **Deletions sync as tombstones** (`lib/repository/sync_tombstones.dart`): deleting projects permanently, unstacking, removing a scan root or ignoring a path, and deleting a release record one; uploads carry them as `deletedRecords`, and a merge drops any row last changed before its tombstone (a release always). A new way of deleting a project or release on purpose must record one, or the union merge brings the row back from the next device. They are sync bookkeeping, not user data: not in local backup.
- **Rows are matched by profile and id, never id alone.** One id can sit in two profiles (old restores copied projects into every profile), so every backup entry carries its own `profileId` (`remoteEntryProfile` falls back to the old `projectToProfile`/`releaseToProfile` maps, which can only name one profile per id), and a tombstone names the profile it was deleted from (`tombstoneFor`). Matching by id alone uploaded a stray hidden copy labelled as the real project, and would let deleting one profile's copy delete the other's.
- **Instants go into synced and backed-up JSON in UTC** (`syncInstant` / `parseSyncInstant`, `lib/utils/sync_time.dart`), and are read back as local time. A local time with no offset names a different moment on a device in another time zone, and two moments in the hour the clocks go back: a restore made at 02:30 on 25 October lost to its own deletion. Dates on the calendar — a deadline, a due date, a release date — stay local dates; a work session's id is its local start time and never changes. A new instant in a synced model's JSON goes through `syncInstant`.
- **A preview song with no file on the uploading device keeps Drive's entry** (`carriedPreviewSongEntry`, `lib/services/preview_song_sync.dart`): the previous backup's, else a `drive://` reference's file, else the file named `<projectId>_preview.<ext>` in Drive's `preview_songs` folder. Only removing the song from its project lets go. The backup used to be rebuilt from the uploader's files alone: a copy missing on a desktop, and every song on a phone (which reads none), dropped out, and every device lost them while the files sat on Drive. Songs not found here are reviewed in Settings > Mixdown folders > Missing preview songs (`findMissingPreviewSongs`, `lib/utils/missing_preview_songs.dart`): sorted into on Drive, another computer's path, folder not there, file gone — by existence checks only — and nothing is cleared unless the user asks.
- **Every overwrite keeps the previous backup** in the backup folder's `history` (Drive-side copy, newest `snapshotsKept`), for "Recover from an earlier backup".
- Errors are shown through `classifySyncError` + `syncErrorSentence`, never by matching English text, and the failure kind is stored so the next launch still shows it. `test/helpers/fake_drive.dart` is an in-memory Drive behind the real `googleapis` client — test sync behaviour against it, not against mocks.

### The DAW plugin talks to the app through files
- The DAW plugin (#118, its own repo: bandpassrecords/daw-project-manager-plugin, C++/JUCE) and the app share `plugin_bridge/` inside the library folder (`dpmPluginBridgePath()`). Its `docs/PROTOCOL.md` is the contract; `lib/services/plugin_bridge/` is this side of it. Change them together.
- The app writes `index.json` (every profile's projects with their to-dos — stacks and archived projects left out, a stack member carrying its stack's to-dos) whenever it changes, and always right after applying the plugin's messages: a fresh `generatedAt` is how the plugin learns they arrived. `launchProjectInDaw` writes `launch.json` just before launching.
- The plugin's `outbox/` messages are applied in file-name order and deleted. Matching is by profile and id, never id alone. A `todo.add` keeps the plugin's `todoId` as the `TodoItem.id` (that is the acknowledgement, and what makes a replay harmless); a tick on a to-do deleted in the app is dropped.
- **A capture is never the preview song**: it has a slot of its own, `MusicProject.latestCapture` (`PluginCapture`: path, `capturedAt`, length; `@HiveField(50)`), and only the latest is kept — a newer one (`dpmPluginKeepsCapture`: later `capturedAt`, so a late message can't put an older take back) replaces it, and the replaced file is deleted only when `dpmPluginCaptureFileInUse` says nothing plays it (a capture promoted with "Use as preview song", or one adopted as the preview before captures had a slot, stays). Letting captures stand in for the preview once let a one-minute capture beat a newer full bounce, and kept any later bounce from taking over. Captures are copied under `preview_songs/plugin/<id>/`. The capture is user data: Drive sync and local backup carry it. **Its file travels on a track of its own**, never through the preview songs' code: the backup's `pluginCaptures` maps `"<profileId>/<projectId>"` to a `CaptureEntry` (Drive file id, hash, name, when, length), one Drive file per project in `plugin_captures`, overwritten in place by a newer take. The rules are pure (`lib/services/plugin_capture_sync.dart`: `decideCaptureUpload` — unchanged hash is kept, a capture whose file isn't on this device keeps Drive's entry for that very take so a phone's upload never takes it from everyone; `captureNeedsDownload` — none here, older here, or same take without its file); the Drive side is a `part` of the sync service (`google_drive_capture_sync.dart`), run at the end of `uploadDatabase` and `mergeData` (skipped with `downloadPreviewSongs: false`). A download is written to `.part`, checked against its hash, then renamed. The project page shows it under the preview (`LatestCaptureSection`, its own player in `AppAudioFocus`); the dashboard's table rows and cards get a capture button only where `dpmPluginDetectedProvider` says the plugin is (found installed, or seen running; never on a phone).
- **Notes travel both ways** (`notes.set`, `applyDpmPluginNotesSet`): the plugin sends the whole text plus the text it began from. It replaces the app's notes only when those still read as it began; if both changed, both are kept, separated by a dashed line. Notes are never silently lost. Every handled message id is listed in the index's `applied` for 30 minutes, which is how the plugin confirms an edit whatever the app made of it.
- **Work sessions follow the DAW** through `DpmPluginSessionHooks` (`RiverpodDpmPluginSessionHooks` in the app). Each running plugin instance (by `runId`, never the saved instance id — copies of a project share that) says hello, keeps a heartbeat in `instances/`, and says goodbye when the host destroys it. A session ends (`WorkTimerNotifier.endAt`, at the goodbye's time or a stale heartbeat's `lastSeen`) only when its project goes from present to absent — never for a project no plugin was in — and for a stack when the last version the DAW had open closes. A gap in the app's own ticks (the computer slept) refreshes every instance, or waking would end the session at bedtime. Starting on hello is opt-in and never switches away from a running session or across profiles. Both switches are device-local (Settings > DAW plugin); `decideDpmPluginSession` is the one rule. A session ended this way is **never ended silently**: `showDpmPluginSessionEndedDialog` gives its summary and why (the DAW closed it, or the plugin stopped responding), with a notification when the window isn't in front.
- **Times from the plugin are UTC ("…Z"); `dpmPluginTime` makes them local on arrival.** `DateTime.tryParse` keeps them UTC and `DateFormat` prints them as such: a session once showed as 12:51–10:52. `sessionEndTime` also returns local, whatever it is handed.
- **Settings > DAW plugin** (`DpmPluginSettingsView`, a plain view the settings page wires up) is the plugin's home: what it does, "last seen in {DAW} (version …)" from the bridge's hellos and heartbeats (`dpmPluginSightingProvider`, device-local, never rolled back by an old heartbeat), a download button for this OS's installer from the newest release (`dpmPluginDownloadUrl`: installer, else the release page, else the releases page — the app never bundles the plugin), "Download the update" when that release is newer than the version last seen, and the two session switches.
- **Installed copies are found on disk, never loaded** (`plugin_install_scan.dart`): the standard plug-in folders per OS, plus the folder the Windows installer recorded (its uninstall key's `InstallLocation`), are checked for `DAW Project Manager.vst3`/`.component`, and the version is read from the bundle's `moduleinfo.json` (JUCE writes it with trailing commas, so strict JSON rejects it — `test/fixtures/plugin/moduleinfo.json` is a real one) or macOS `Info.plist`. The user's own folders (device-local) are searched **only when the standard ones have no copy**. Two copies of one format are flagged: the DAW may load either. The Flatpak can't see the folders, so it doesn't search (`dpmPluginScanAvailable`).
- Desktop only, on a 3-second timer started in `main.dart`. Tests run against `DpmPluginLibrary`/`DpmPluginSessionHooks` fakes and a temp folder, never Hive. Nothing new is stored: to-dos, `previewSongPath` and sessions already sync and back up.
- **The two sides are also tested together** (`test/plugin_integration/`): the real `DpmPluginBridgeService` on a real Hive library in a temp folder, and the plugin's own bridge code through its headless driver (`DAWProjectManagerBridgeDriver`, a console target in the plugin repo: one `BridgeSession` with no DAW, driven a JSON line at a time, `plugin_driver.dart`). Nothing writes a message by hand; clocks are set on both sides, so staleness is tested without waiting. Locally the tests find the driver in the plugin repo built next to this one (or `DPM_PLUGIN_DRIVER`) and **skip** without it; CI's `plugin_integration` job builds it at the commit in `test/plugin_integration/plugin_ref` (a released plugin, v0.1.0 on) and fails if it can't; every build and release job waits for it. A protocol change updates both repos and that pin in step. A new message type or behaviour gets a scenario there, not only a fake-backed one.

## Architecture

### State management — Riverpod
- All providers live in `lib/providers/providers.dart`.
- Main data flow: `repositoryProvider` → `allProjectsStreamProvider` → `projectsProvider` (filtered/sorted) → UI.
- Search state is per-tab: `projectsSearchProvider`, `releasesSearchProvider`, `queueSearchProvider`, etc.

### Local persistence — Hive CE
- Models with `@HiveType` / `@HiveField` and a `part` directive (e.g. `Release`, `TodoTemplate`) use code-generated adapters — run `dart run build_runner build --delete-conflicting-outputs` after changing them.
- `MusicProject` and other models have manually written `TypeAdapter`s inline in their model file — `build_runner` skips these intentionally.
- Adapters are registered in `ProjectRepository` with `isAdapterRegistered` guards to prevent double-registration.

### Platform detection
- Use `MobileUtils.isMobile()` (from `lib/utils/mobile_utils.dart`) for mobile vs desktop checks — not `Platform.isAndroid` or `Platform.isIOS` directly.
- Desktop = macOS + Windows + Linux. Mobile = Android + iOS.
- Primary development and test target is **macOS**.
- Linux is otherwise a full desktop target. The only feature gaps are inside the Flatpak build: Google Drive sync (see `GoogleDriveSyncService.isSupported` above) and MIDI keyboard input (`MidiInputBackend.isSupported`, no `--device=all`) — the tarball/AppImage have both.

### Themes — every theme is a `CustomTheme` spec fed through one builder
- There is exactly **one** `ThemeData` builder: `AppThemes.buildFrom(CustomTheme)` in `lib/providers/theme_provider.dart`. The three built-ins are `CustomTheme` constants (`neonDarkSpec`, `classicDarkSpec`, `studioLightSpec`) run through it, and user themes go through the same call. Never hand-write a second `ThemeData` — a component styled in only one builder is a component user themes fall back to raw Material defaults for.
- `test/providers/built_in_theme_regression_test.dart` keeps a verbatim copy of the pre-refactor themes and asserts `buildFrom` still reproduces them. If you change `buildFrom`, that test tells you which built-in you moved. Its one accepted deviation (`studioLight`'s `bodySmall` tone) is documented in the file.
- Two active themes: `AppThemeType.neonDark` and `AppThemeType.classicDark`. `AppThemeType.studioLight` exists in the enum but is hidden from the UI until it is ready — `AppThemes.visibleBuiltIns` is the list every menu, switcher and picker must use; `allBuiltIns` is only for resolving a stored id.
- The active theme is identified by a **string id**, not an enum: `selectedThemeIdProvider` holds either an `AppThemeType.name` or a user theme's uuid, and `activeThemeProvider` resolves it to a spec (falling back to Classic Dark for anything unknown). Watch `themeDataProvider` for colors and `activeThemeProvider` when you need the spec.
- **Never branch on theme identity.** `themeType == AppThemeType.neonDark` used to pick grid row colors in four places, which silently lumped every user theme in with Classic Dark. Derive from the spec instead — `hasVividAccent`, `gridRowSelectColor`, `gridRowOddColor`, `gridRowEvenColor`, `gridBorderColor` in `lib/utils/theme_derivations.dart`.
- A widget that caches colors (any `TrinaGrid`) must key on `spec.identityKey`, not `spec.id` — editing a user theme keeps its id, and the id alone would leave the old palette on screen.
- User themes are **dark-only in v1**: the editor pins `brightness` to `Brightness.dark` because large parts of the UI still carry hardcoded `Colors.white70`-style literals that vanish on a light background. Unlocking the toggle is the same work as finishing `studioLight`.
- Theme *definitions* are user data: they sync to Drive and go into local backup (see `mergeCustomThemes` in `lib/services/custom_theme_merge.dart`, shared by both so a restore and a sync can't disagree). The *selected* theme is a device-local preference and is deliberately in neither.

## UI conventions

### Where these features meet each other
- **A new `@HiveField` index must be chosen against `main`, not against your branch.** Four branches independently claimed 38 because it was next-free on each of them, and git merged all four silently — a duplicated index is data corruption, not a conflict. `test/models/music_project_test.dart` now asserts indices are unique, that `writeByte(n)`'s count matches the highest index + 1, and that every declared field is actually written.
- **Two accent colours, on purpose.** `projectAccentColor(MusicProject)` in `project_visuals.dart` is the user's override and is *nullable* — a list row with nothing chosen draws nothing, which is #110's whole point. `derivedAccentColor(String id)` in `project_accent_color.dart` always returns one. `resolvedAccentColor` layers them and is what a **card** uses, because a card is mostly artwork and cannot be left blank. Don't use the resolver for rows or badges; don't use the nullable one where something must be painted.
- **A card honours the full visual stack**: cover art → chosen icon → chosen/derived colour with initials. Anything added to `ProjectCardGrid`'s cover has to keep that order, or the appearance editor's choices stop showing up.
- **Archiving gathers out-of-folder attachments** (`attachmentsToGather`) into `_attachments/<id>/<basename>` in the zip, keyed by id so two `notes.pdf` can't collide. Links have no bytes; attachments already inside the folder are picked up by the walk. `deleteOriginals` still only ever deletes the project's own files — an attachment in `~/Downloads` is not ours to delete. `repathRestoredAttachments` repoints a gathered attachment on restore **only** when its original has since gone away.
- **Moving repaths attachments** under the moved prefix (`repathProject`). The lyric sheet beside the project file is the common case and a move that ignored it would break every one.
- **Relocating a scan folder** (`ProjectRepository.relocateRoot`, Settings > Project folders) is for files the user moved themselves — a cloud drive emptied on one disk and downloaded on another: nothing is read, copied or moved. Everything naming a path inside the folder follows it through `rebasePath` (`lib/utils/path_rebase.dart`, the one rule `repathProject` uses too): every project (`repathProject`, with a fresh `updatedAt` so the move syncs), the excluded paths inside it, and the projects in Recently deleted from it. A path left behind is a project the next scan adds again, empty, or an exclusion that stops working. A new path field on a project goes in `repathProject`; a new kind of stored path under a scan folder goes in `relocateRoot`. Before it changes anything, `RelocateFolderDialog` shows `previewRelocation`: how many of the folder's projects are already at the new place, by asking the filesystem for each entry's type only — reading a cloud placeholder would download it.
- Cover art lives in the app-managed `project_cover_art` folder (`app_paths.dart`), so it is untouched by moves and archives and rides along in Drive sync / local backup instead.
- **One image file can belong to several rows.** A version stack is a copy of its promoted member, `thumbnailPath` included, so the stack and that member share one cover file. Never delete a managed image without first asking `isImageInUse` (`lib/utils/cover_art_refs.dart`), after the row that let go of it has been saved. Deleting it outright once broke the member's cover the moment the stack's changed. Release artwork carried over from a project is **copied** (`copyArtworkForRelease`), never pointed at the project's file.
- **Stacking promotes a member's look along with its details.** `MusicProject.hasSomethingToPromote` (details *or* cover/colour/icon) decides both whether to ask and the default, and `preferredStackMetadataSource` (`lib/utils/version_stacks.dart`) is the one default rule. It picks the oldest member with something to promote, never a blank older one. The dashboard and automatic folder stacking both use it.
- **Tags are case-insensitive and only written through `lib/utils/project_tags.dart`** (#109). `canonicalTag` resolves typed text to the library's existing spelling, and `addTag`/`removeTag` refuse case-only duplicates. A hand-rolled `[...tags, x]` is how "Trap" and "trap" become two filters. `availableTagsProvider` is computed over the whole (stack-collapsed) library, never the filtered list, and `effectiveTagFilter` drops a filter on a tag nobody has any more. The whole feature sits behind the device-local `tagsEnabledProvider` (Settings > Appearance, **off by default**): off hides every tag surface and empties `availableTagsProvider`, but the tags stay on the projects and keep syncing.
- **Markers over a row's cover-art bleed need an opaque backing.** Use `on_art_marker.dart`: `onArtCapsule` for text badges, `OnArtMarker` for status icons (a disc only on rows with artwork), and `onArtTextHalo` for the name. A translucent tint disappears into a busy cover.

### What is inside a project: stats and MIDI clips
- `MusicProject.stats` (`ProjectStats`: track counts by kind, plug-in names, clip count) follows the **markers' null contract**: null means "never read", and a lightweight scan passes null so the last deep scan's value stands. It is scanned, yet it syncs and backs up — a phone or a Flatpak restore without the project folders cannot re-read the file.
- MIDI clips are **stored per project in their own lazy box** (`MidiClipStore`, `<profileId>_midi_clips`), never on `MusicProject` — the projects box is loaded whole and rewritten on every edit. Every full-metadata extraction replaces them; a lightweight scan never touches them. They sync to Drive and go into local backup under `midiClips` (project id → `StoredMidiClips.toJson`), merged with `MidiClipStore.mergeNewer`: newer `extractedAt` wins, nothing is deleted. Deleting a project deletes its clips.
- The first read is still behind a button: the project may sit on a cloud drive where reading means downloading.
- A deep scan reads contents too, and its "only projects not fully read yet" mode goes by `needsDeepScan` (`lib/utils/deep_scan.dart`), never `metadataScanned` alone: a project deep-scanned before contents could be read has `metadataScanned` but null `stats`, and checking the flag alone skipped it forever. A new reader (another DAW's contents) needs its extension in `MetadataExtractor.readsProjectContents` for the same reason.
- **A collection can start a blank clip** (its "New clip" button, `newMidiIdea`: one empty bar at `kNewIdeaBpm`, shown four bars wide via `minViewTicks`, its length then following its notes), opened editing (`showMidiPianoRoll(startEditing: true, lengthFollowsNotes: true)`) — with the select tool, as entering edit mode always is. Nothing bounds it while it is drafted — no loop region, and playback is **open-ended** (as it is for **any** clip while it is being edited: the clip has no end there, so playback never stops by itself, notes left or not; only a cycling loop region bounds it — just listening, a clip ends. With an editor the playhead and the ruler aren't held at the clip's length either (`playheadTick`, `_clipEnd`): held there, a one-bar draft looked as if playback stopped at its first bar): rendered into silence past its notes (`openEndedHorizon`, never looped) and rendered further, taken over without a gap, as playback nears the end (`needsLongerHorizon`), so it plays until stopped. Saving sets the loop region to its length, the end of its last bar with notes. A clip with a length of its own opens with the loop region spanning it. Saving puts it in the collection with `MidiCollectionStore.putItem` under one item id, so saving the idea again replaces it rather than adding a copy per save.
- **A collection names its own files** (`lib/models/midi_clip_naming.dart`). `MidiCollection.naming` (`MidiNamingTemplate`: numbered, ordered `MidiNameField`s, separator) and `folders` (`MidiCollectionFolder`, nested by `parentId`), and per item `title` (blank: the clip's label — the clip itself is never renamed), `role` (a `MidiClipRole` name; null: `suggestMidiClipRole` from names, then voice, then notes) and `folderId` (null, or a folder that's gone: the top level). A folder's order **is** the items list's order filtered to it — `reorderInFolder` swaps which of its clips sit in its slots, nothing else moves — and that order is the file number (`planCollectionExport`, zero-padded to the folder's widest). Every exported name goes through `midiItemFileName`; the bar count and time signature come from the item's time signature, the grid from `midiClipGrid` ("free" when the notes keep to none). Deleting a folder moves its clips and folders up a level; `moveFolder` refuses a folder's own descendants, and `folderPath`/`foldersIn` survive a parent loop a merge of two devices' moves could make. All of it rides in the collection's JSON, so sync and backup need nothing extra. A drafted clip asks for name, role and folder on its **first** save only (`ideaItemToSave`); later saves keep what the saved copy has, renamed or moved since. `MidiExport.name`/`folders` carry the plan to `exportAll`, which makes names unique per folder; `zipMidiFiles(root:)` keeps the tree. **Scheme names**: `midiSchemeName` is a clip's name made of the template's pieces other than the name ("Bass - 140BPM - Am - 4 bars", for a clip named "MIDI 01"), offered in the rename dialog and proposed for many clips at once by `MidiBulkRenameDialog` (every name editable, untick to leave one out; `renameItems` returns the old titles for undo, `uniqueClipNames` numbers repeats). So a clip named by the scheme doesn't say it twice, `midiTemplateFileName` leaves out a piece the name already contains **as a whole piece** (split on the separator, " - " and "_") — never a word inside a name.
- **The MIDI tab's collections are trees, and things drag** (`lib/ui/widgets/midi_collection_tree.dart`): the side list (`MidiCollectionNavigator`) opens each collection on its folders, a collection's view (`MidiCollectionTree`) opens folders on their subfolders and clips, indented. One drag mechanism, Flutter's `Draggable`/`DragTarget` (`midiDragSource`, `MidiDropZone`; long press on a phone), carrying a `MidiDragData` (`lib/models/midi_collection_drag.dart`): a collection's clip moves (onto a folder: at its end; onto a clip: just before it, `moveItemsToFolder(beforeItemId:)`; onto another collection: `moveItemsToCollection`, which writes the target first so a crash leaves a copy, never a loss), a folder moves into another, a clip from all clips is copied in. `canDropMidi` is the one rule for what may land where — a folder never into itself or below itself, folders never between clips or across collections. A drag resting on a closed folder opens it (`MidiDropZone.holdDelay`). The row's grab area (thumbnail and names, `MidiClipList.grabWrapper`) is separate from its handle, which still drags the `.mid` file out of the app. What is open — side list, collection tree, all clips' groups (by project and by tempo keyed apart) — is `MidiTreeState`, kept by the **device-local** `MidiTreeStateStore` (neither synced nor backed up), with expand/collapse-all buttons on each; `MidiClipList.groupOpen`/`onGroupToggled` let the caller keep its groups.
- **MIDI collections hold copies, never links** (`MidiCollection` / `MidiCollectionStore`, `<profileId>_midi_collections`): a collection keeps working after its source project is edited, re-extracted or deleted, and shares as a self-contained set of files. Deleting a project never touches them.
- Deleting a collection writes a **tombstone** (`deleted: true`, newer `updatedAt`) instead of removing the record. Collections merge with the union rule, so a plain delete would be undone by the next sync from a device that still had it; the tombstone wins instead. Anything reading collections must skip tombstones (`all()` does by default); only sync and backup ask for them.
- The MIDI tab (`midi_library_page.dart`) lists `buildMidiLibrary` — unique clips across all of a profile's projects — and collections. It and a project's clip section both play through one `MidiPreviewPlayer`, keyed by clip, never by list index.
- **Editing never changes a project's clips** — they are re-read from the DAW file on every scan. The piano roll edits through `MidiClipEditController` (`lib/ui/widgets/midi_clip_edit_controller.dart`): a drag previews from the state the gesture started in and `endGesture` makes it one undo step; edits act on a **selection** (a set of note indices), never on one note, so a box-select, a Shift-click and Ctrl+A all move, transpose, resize and delete the same way. Gestures copy Cubase's key editor, with its tools and their keys (`MidiEditTool`): with **select** (1), a double-click adds a note — on the second **press**, so holding on and dragging draws it exactly as the pencil does (across: length, up/down: velocity, Ctrl: off the grid, the start included) — or deletes the one under it, a drag on empty space draws a selection box, Alt-drag moves copies (an unmoved copy is dropped, not left on its original); **range** (2) selects a stretch of time and every note starting in it; the **eraser** (5) deletes whatever a click or a drag passes over, notes or lane points, as one undo step; with the **pencil** (8), a click adds a note and stretches it as it drags (`beginNote` — one undo step), up or down setting that note's velocity only (the next note starts from the usual velocity again); it **never deletes** — a click on a note selects it (deleting is the eraser's job, and an accidental click while drawing must not lose a note). Ctrl/Cmd+D `duplicate`s: a range straight after itself (cut at its end, events too, the range moving onto the copy so it can go again), or the selected notes from exactly where the last one ends — off the grid if that's where it ends, on purpose; the range is the on-grid way. Q `quantize`s note starts (the selection, or every note). Every key-only action also has a toolbar button — duplicate, quantize, a transpose menu — because a phone has no keys. **A clip grows with its notes**: `_commit` runs `grownToNotes`, so a note past the end lengthens the clip to that bar (undo shrinks it), and while editing the canvas is endless (always a view's width past the scroll, zoom out to 1/16 of fit). With either, a note's outer edge resizes from that side (`noteEdgeAt`), Ctrl ignores the grid, ↑/↓ transposes a semitone and Shift an octave without bending a chord at the keyboard's ends. A drag across the velocity lane sets every note it passes (`drawVelocities`); controller and pitch bend lanes are drawn along the line between pointer samples at `laneStepTicks` (a 128th note), **never at the note grid** — on the 1/16 grid a bend was a staircase — and a bend near the middle snaps to no bend (`snapLaneValue`). Zoom keeps the time under the mouse still and switches follow off, or the next frame's follow scroll would undo it; vertical zoom keeps the notes in focus (`verticalZoomScroll`); notes keep their order while editing (an index stays the same note) and `finished` sorts them for saving. The window's `onSaveEdited` saves the result as a **new** clip in a collection, keyed `<playerKey>~edit` while it plays. Pitch bend and the mod wheel are always offered as lanes (`availableMidiLanes`), empty or not, so they can be drawn in.
- **The transport never hides stop.** While a preview renders, a spinner stands where play is — only there; stop stays, and cancels the render. The whole transport turning into a spinner made stop vanish and come back on every render.
- **A click on the ruler never starts playback; a double-click does** (`onPlayFrom`). Playing (or paused), a click jumps there; stopped, it only moves the start (`_startFrom`), the line resting there (`restTick`), and the next play starts from it. The double-click is told from the presses' own timestamps (`_onRulerPress`), never a `GestureDetector.onDoubleTap`, which would hold every single click back for the double-tap timeout. A tempo change keeps the start on its tick. Stop is always in the header: playing, it stops; stopped, it takes the start back to the beginning.
- **The window's keys stand aside while a text field has the keyboard** (`_WindowKeys`, `isTypingInTextField`): typing "8" into the tempo must not pick the pencil, nor Space start playback. Esc or Enter in the field, or a press anywhere outside it (`_takeKeysBack` — a desktop text field keeps the keyboard when you click away), gives the keys back, and focus that falls back to the window's route is taken back at once (`_reclaimKeys`). A new shortcut goes in its bindings, never in a `CallbackShortcuts` of its own.
- **Every shortcut and gesture is on one sheet** (`MidiShortcutsSheet`, opened from the window's keyboard button, `?` or F1; rows built by `midiShortcutSections`, with keys named as a Mac prints them on a Mac). Not tooltips, and not hints that pop up while editing — both were tried and got in the way. A new key or gesture gets a row there.
- **What plays is what is on screen** (`_playingStale`): an edit (or an undo back to the clip as opened) takes over from **whichever** version is playing — the clip as opened too — and resuming after an edit made while paused restarts what is on screen from the same spot. Only swapping an edited version that was already playing left deleted notes sounding — ghosts — when playback had started before the editing.
- **An edit to a playing clip takes over** (`MidiPreviewPlayer.play(takeOver: true)`): the old audio keeps playing while the edited clip renders, with no "preparing" state, and the new one starts from wherever playback has got to by then. A plain `play` stopped the sound and flickered the transport on every edit.
- **The window has a tempo, a time signature and a loop region of its own.** `EditedMidiClip` carries tempo, `TimeSignature` (`lib/utils/time_signature.dart`), key and instrument to whoever saves, and a collection item keeps the time signature (`MidiCollectionItem.timeSignature`, JSON `timeSig`, omitted for 4/4) so its `.mid` says it (`MidiExport.timeSignature`). Bars everywhere — grid, ruler, lane, how far a clip grows — come from the time signature, never `ppq * 4`. The loop region (Ctrl/Cmd-click on the ruler sets its start, Alt-click its end; its purple ends drag to resize it and its middle to move it, on the grid; a hand only over its ends; a plain click on it turns looping on or off — it and the header's loop button are one switch, and it is light grey while off. It lives in its own strip along the top of the ruler (`kLoopStripHeight`) with the bar numbers below it, and only presses in that strip touch it; below, a click jumps) is played with `loopRegionClip` while looping is on; positions are mapped back into the whole clip (`_between`), and a region dragged while cycling restarts playback once it settles, not on every step. While editing the clip's end isn't drawn: a clip being edited grows with its notes, and a drafted one (`lengthFollowsNotes`, `fittedToNotes`) is exactly as long as its notes.
- Drags near the edge of the notes scroll the view (`autoScrollVelocity`); a drag measures from where it started **on the notes** (`scrollStart`), so what it carries keeps up with the scroll. Ctrl/Cmd+click adds to the selection like Shift+click, and takes an already selected note out; Ctrl-drag still moves off the grid. With two or more notes selected, the velocity lane only changes those.
- `MidiPreviewPlayer.play` reads where a taken-over clip had got to **before** stopping it (`takeOverStart`) and loads, seeks, then starts the new audio — reading after the stop always gave 0, and every edit, undo or redo restarted the clip. Through the swap (`_swapping`) the player's position reports are ignored and the held clip's position keeps extrapolating, taken again just before the new audio starts: the stop's rewind to 0 made the playhead — and the followed view — jump to the start and back on every note drawn while playing.
- The window can fill the whole app window (its full screen toggle, device-local `MidiPianoRollFullScreenStore`). It stays **one** `Dialog` whose insets and size change, so switching keeps the window's state and unsaved edits. A middle-button drag moves the canvas, with a **drawn** hand in place of the pointer (Windows has no grabbing cursor: asking for `SystemMouseCursors.grabbing` there shows the plain arrow).
- **The piano roll sounds notes** through `MidiNoteAuditioner` (`lib/ui/midi_note_auditioner.dart`): a key clicked on its keyboard always (and each key a drag along it passes) — for as long as it is held (`hold`/`release`: a 4 s held render, faded out on release; a quick click is a 16th blip; a voice that sustains — `sustainsWhileHeld` — crossfades, 3 s in, into a seamless loop of the note's steady middle cut from that same render, `sustainLoopWav`, so it lasts as long as the key does) — and with the device-local acoustic feedback toggle (`MidiAcousticFeedbackStore`) a note drawn, clicked, dragged to another key or transposed. The window's instrument picker changes what both the clip and those notes play with; `onPlay` and `SaveEditedMidiClip` carry the voice, so the list and a saved edit keep it.
- **A MIDI keyboard plays into the piano roll** (`lib/services/midi/input/`). No plug-in: `flutter_midi_command` 1.x needs `win32` 6, which `file_picker` and `share_plus` block, and 0.5 made Bluetooth LE a *required* feature on Android. So each platform reads its own: Windows `winmm` through `win32` (`NativeCallable.listener` for its callback thread; an input there is one app's at a time, so the window opens the chosen input only while it is open, and a busy one shows red), Linux the ALSA sequencer through FFI on an isolate of its own (shared with a DAW), macOS/iOS CoreMIDI and Android `android.media.midi` behind one channel contract (`ChannelMidiInput`; `MidiInputBridge` in `MainFlutterWindow.swift`, `AppDelegate.swift`, `MidiInputBridge.kt`). Backends hand over raw bytes; `MidiByteParser` (one per input: running status belongs to its stream) makes messages. Which input — none, all, one by **name** (ids change between runs) — is `MidiInputChoice`, device-local (`MidiInputChoiceStore`), off by default. **Not offered inside the Flatpak** (`MidiInputBackend.isSupported`, the same `/.flatpak-info` test as Drive sync): `/dev/snd/seq` needs `--device=all`, which the Flathub build deliberately doesn't ask for — no button, no shortcut-sheet section, nothing opened. A key held sounds through the auditioner's `hold` and is lit on the roll's keyboard (`playedKeys`). **Recording** (the transport's record button, or R; there is no step input — it was tried and replaced) starts editing and plays the loop region, cycling whatever the loop button says (`_activeRegion` counts `_recording`; a drafted clip with no region gets four bars). Each key goes in where the playhead was as it went down (`_nowTick`, off the grid, as played), as long as it was held (held across the loop's end, it stops there), at its velocity; a whole take is one undo step (`addPlayedNote(joinTake:)`). Recorded notes take over playback 400 ms after the last one (`_recordedTakeOver`), so the next pass plays them without a render per note. Playback stopping for any reason ends recording (`_onPlayer`, checked a microtask later so a restart's stop-then-play doesn't). **Recording latency** (device-local `MidiRecordLatencyStore`, 0–`kMaxRecordLatencyMs`) is taken off every recorded position by `recordedTick` (`lib/utils/midi_recording.dart`; just after a cycling region's start it wraps to the pass before): it is the whole round trip — playback reaching the speakers after the player reports it, the key reaching the app — so it is measured, not guessed: **calibrating** (the MIDI input menu's latency dialog) loops a bar of clicks under `calibrationKeyOf`, takes `kCalibrationTaps` keys, and `measuredLatency` is the median of how late they came after the nearest click. It records nothing.
- **The metronome is rendered into the preview, never played beside it** (`Metronome`, `MidiClipSynth.renderWav(metronome:)`): clicks timed in Dart would drift from the audio; rendered, they are sample-exact and loop with it. A click on every `TimeSignature.beatTicks`, accented on the bar's first, `offsetTicks` = the loop region's start so a cut-out region still clicks the clip's own beats. It is its own preview cache key (`cacheKey`), so a render without clicks is unchanged — no `kPreviewRenderVersion` bump. The toggle (and C, as in Cubase) is device-local (`MidiMetronomeStore`); clicking, the window plays the clip itself (the list's `onPlay` has no clicks) and restarts on a change of time signature. The player keeps a play's loop override and metronome in `_current`, so switching looping restarts with the clicks, and a play asked to loop whatever the setting (recording, a draft) is left alone by `setLoop`. Never await `close()` on a stream controller nobody may have listened to — it never completes; that once kept the input open after the window closed.
- **Scales** (`lib/utils/musical_scale.dart`): the piano roll opens on `scaleFromKey(project key)` and shades rows outside it, and draws notes outside it — and their velocity stems — orange (`noteOutOfScale`). A selected note is drawn inverted: black inside, its colour (green or orange) on the outline and name; `MusicalScale.keyText` reads back as the same scale and, where it has one, as a key signature, which is how a saved edit keeps the scale it was made in.
- **Looping a preview renders a different WAV**, not just the player's repeat flag: `renderWav(loop: true)` is exactly one pass of the clip (`loopSeconds`) with the tail past its end folded back onto the start, so it repeats seamlessly in time; the preview cache keys it with `_loop`. `MidiPreviewPlayer.setLoop` re-renders and carries on from the current spot (on resume if paused), and `positionOf` wraps with `wrapLoopPosition` so the piano roll's line follows each pass. The loop setting (`midiPreviewLoopProvider` / `MidiPreviewLoopStore`) is device-local, like the preview volume.
- The piano roll (`midi_piano_roll.dart`, opened from a clip's thumbnail) runs its frame ticker **only while its clip plays** — not while paused either: a paused position doesn't move, so the ticker stops on the first unchanged frame — driven by the player's notifications. An always-on ticker keeps the app rendering every frame for nothing and makes `pumpAndSettle` time out.
- Per-format readers live in `lib/services/daw_parsers/` and return values for `MetadataExtractor` to merge — stats are a bonus there, so a parser failure costs the stats, never the tempo/key/notes.
- **Cubase archives count by back-reference.** A class name is written once; every later object of that class is `0x80000000 | (definition offset − ARCH start)`. Counting names finds one audio track in a project with forty. The format notes are on `CubaseProjectParser`.
- A clip holds only what plays: `windowMidiNotes` drops material trimmed off a part's edges and unrolls loops.
- **Every `.mid` the app writes goes through `MidiExport`** (clip + tempo + the source project's key). The key becomes a key-signature event (`keySignatureOf` in `lib/utils/musical_key.dart` reads "A minor", "F#m", "C# Dorian", Camelot "8A"…) and a `(key)` suffix on the file name. A collection item stores the key it was copied with (`MidiCollectionItem.musicalKey`, JSON `key`), like its tempo, so a collection exports each clip at its own project's tempo and key.
- **Preview voices** (`SynthVoice`): a clip's instrument is a stored name, so retiring a voice is safe — a name this build lacks reads as no pick and is inferred again. `synth` was retired that way (it sounded all but the same as `bass`); the fallback for a clip nothing identifies is `keys`. Each voice must sound like itself: `voice_distinctness_test.dart` renders them all and fails any pair with the same tone and start, or too alike overall — keys was once a bass with a decay. Rendered previews are cached by name, so **any change to how the synth sounds bumps `MidiClipService.kPreviewRenderVersion`**, or old renders keep playing. A rendered preview fades to silence over its last `kEndFadeSeconds` and then carries `kEndSilenceSeconds` of true silence (a loop has neither): Windows' player plays out its last, part-filled buffer with leftovers at the end of a file — the "glitch after the sound" — and ending on silence makes that leftover silent, and stopping or pausing — the clip, or a held note let go — fades out first through `fadeOutAndStop` (`lib/services/audio_fade.dart`): many small steps to true silence, never a few big jumps, which were clicks themselves.
- **`.mid` files from anywhere can be imported into a collection** (`importMidiFilesFlow`, MIDI tab). `importMidiFile` makes one clip per track with notes, each the full file length and never pattern-shrunk, with the file's tempo and key. Imported items have no source project, only `sourceFileName` (JSON `sourceFile`); `MidiClipList.canOpenProjectOf` hides "Open project" on them. They live only in collections, never in the project-built library.
- **REAPER items can reference a `.mid` file** (`FILE "…"`, no `HASDATA`). The parser never touches the disk itself: callers pass `projectDir` and `readFile: readBytesIfExists`, and `decodeMidiFile` (`lib/services/midi/midi_file_reader.dart`) turns the bytes into the same notes/events the embedded path produces. Files that can't be found or read come back as `missingFiles`, are stored on `StoredMidiClips.missingFiles` (synced and backed up with the clips) and shown as a warning on the project page (#143).
- The dashboard's "Only projects with MIDI" toggle (`hasMidiFilterProvider`, session-only) is `projectHasMidi` (`lib/utils/project_midi.dart`): a full read found at least one clip; a stack counts when a member does. The MIDI tab can arrange clips by tempo (`sortByTempo`, grouped under BPM headings), also session-only.
- **Clips carry their events** (`MidiClip.events`: controllers, pitch bend, aftertouch, program changes), windowed by `windowMidiEvents` with the same window and loop — which also *chases*: a lane's last value before a trimmed start or a loop pass is restated there, as DAWs do. Events are always `normalizeMidiEvents`'d (one value per lane per tick, repeats of the current value dropped), or a held controller would stop a looped clip from shrinking to its pattern. CC 120–127 (`isChannelMode`) are housekeeping — REAPER ends every source with All Notes Off — and readers drop them. REAPER and Ableton read events (Ableton: clip envelopes on the track's `ControllerTargets.N`, N = 0 pitch bend, 1 channel pressure, 2+ CC N − 2); Cubase and FL Studio don't yet. Events are packed as their own `events` blob, written only when a clip has any, so older builds ignore it.
- **Clips are unique by what they play, never by name.** `dedupeMidiClips` (every format goes through it) first shrinks a clip that only repeats a shorter whole-bar pattern to that pattern, then merges clips with equal `contentKey` — notes and length at a common 960 PPQ; name, track and channel excluded. Velocity, pitch and events stay in the key: a transposed, re-voiced or re-bent copy exports as different MIDI, so it is a different clip. A clip with no events has exactly its pre-events key, so stored clips and collections kept their identity when events arrived.

### The sample pack: read fresh, written to a folder, nothing stored
- Settings > Experimental > "Sample pack from your projects" (`SamplePackCard` → `_exportSamplePack`). It copies the audio files the chosen profiles' projects use into one folder, sorted into category folders, and writes `sample_pack_report.csv` (how many **songs** use each sample — a version stack's members are one song — its origin, length, source) `sample_pack_missing.csv`, and `sample_pack_tree.txt` (the whole folder drawn as a tree by `folderTreeText`, `lib/utils/folder_tree.dart`, rewritten every run so it shows the pack as it is — files the user moved included). Nothing about samples is stored in the app, synced or backed up: every export re-reads the project files. Only the dialog's choices (`SamplePackPrefsStore`: library folders, which profiles — or which picked projects — and the switches) are kept, **device-local**. The dialog can limit an export to projects picked from a searchable list (`SamplePackProjectChoice`), for trying it on one song.
- Each format's parser has `readSampleReferences()` returning `SampleReference`s (`lib/models/sample_reference.dart`): **candidates**, never one path, because stored paths go stale (moved projects, changed drive letters, FL 7's `\Patches\…` relative to a dead install). Cubase: the pool's `FNPath` objects (name, then folder); the Sampler Track's sample is an `FNPath` inside a `PSamplerTrackAudioClip`. Ableton: every `SampleRef/FileRef` — clips, Simpler, Sampler, Impulse, Drum Rack — `Path`/`RelativePath` (Live 11+) or path elements (`Dir=""` is `..`) + `Name` + UTF-16 hex `Data` (Live 9/10). FL: event 196 per channel. REAPER: audio `<SOURCE` `FILE`s. Studio One: `Song/mediapool.xml` URLs. Third-party sampler state is searched with `findEmbeddedAudioPaths` (absolute paths as text, ASCII or UTF-16); Kontakt and Serum compress or embed, so they stay invisible.
- `SampleLocator` tries the candidates, then the project's own folder tree by name (trusted — it is the project's), then the user's library folders — where a same-named file is only taken when it **agrees** with the project: its recorded size, or else the folder it was in. A library holds many "Kick 15.wav"s; the wrong one in the pack is worse than a line in the missing report.
- **One project at a time, copying as it goes** (`_Run` in `sample_pack_exporter.dart`): the folder fills while it runs, and Stop keeps everything done so far — the report and manifest are written then too. Reading everything first and copying at the end left an empty folder after a stop.
- **Never open a file that won't be copied.** On a cloud drive (Proton Drive keeps the library as Windows cloud placeholders) reading even a file's header downloads all of it and leaves it on disk. Own audio is recognised without reading: what the project says, folder names, and the size (`kLongAudioBytes`, which `File.length` gives from metadata); only a sample that is going in gets its length read, its hash taken or its bytes copied. A sample's length, when it is already in the pack, is read from the pack's copy.
- Samples are told apart by **content**, not path (size first; a streamed SHA-1 only when sizes match), so one kick copied into fifteen projects is one sample used fifteen times. Exporting again into the same folder compares against everything already there — wherever the user moved or renamed it — so nothing is copied twice; `sample_pack_manifest.json` keeps each pack file's size/date/hash so unchanged files aren't re-hashed.
- Recordings, bounces, freezes, renders and anything over `kLongAudio` (stems) are **own audio** (`SampleOrigin.isOwnAudio`), left out unless asked for, and then kept apart in `kOwnAudioFolder`. A file **loaded into a sampler** (`SampleUse.sampler`) is a sample whatever its name or folder says — only its length can make it own audio: the Sampler Track in a real project plays `kick-01.wav`, which the `-01` rule would otherwise have left out as a bounce. Otherwise what the DAW says wins (Ableton's `Samples/Recorded|Processed`, a Cubase take named after its track, `-01` beside its original), then render/record folders under the project. Inside a project, only its subfolders inform the category — the project's own folder is named after the song.
- **Master projects are left unread by default** (`isMasterProject`, `lib/services/sample_pack/master_project.dart`): a song's mastering session holds its stems and mixdowns, not samples. One is recognised by the **end** of its name — "master"/"mastering" or a lone capital "M", in brackets or not, before a version number ("(Master)", "(M)-1", "(AC RMX 2025 M)") — or by a "Master Project"-style folder ("Master project New", "Master Project2", "Song - Master"). Only the end counts, so "Master of Puppets (Remix)" is a song. The rule was tuned against a real library of 35 masters and 80 regular projects; widen it with a test case, not a guess.
- **Renaming is an option, off by default** (`SampleNaming`, `lib/services/sample_pack/sample_naming.dart`): `Kick 001`, then whichever of the original name, BPM and key are on, with an optional prefix. Matching never goes by file name — it goes by content — so renamed files are recognised on the next export like any other; only samples a run **adds** are named, and numbers carry on from the highest already in the folder (`nextNumber`), never renumbering what's there. Tempo and key come from the file name, then its nearest folders (`sampleTraitsOf`), then — for a loop only, when its length is whole 4/4 bars at it — its project's tempo (`bpmFromLoopLength`); a one-shot keeps no tempo. A key is only read in an unambiguous form ("F#m", "A minor", "G Phrygian", a sharp/flat note alone), never a bare letter. Both go in the report's `bpm`/`key` columns, renamed or not.
- Category guessing reads a file's name and up to four nearest folders, but **two-letter shorthand ("bd", "sd", "hh") only from the name**: in a folder it was a random temp-folder suffix in tests, and could be anything on a real disk. "FX" is the exception.
- Folder names, file-name prefixes ("Kick - RIM15.wav") and the CSV columns are English on purpose, like the MIDI exports' file names: they are files read in a DAW's browser, not UI.

### An archived project is not a missing one
- Archiving (#116) zips a project out of the working library and sets `archivePath` / `archivedAt` / `archiveEntryPath`. `filePath` deliberately keeps naming the **original location** — it is what `fileExtension`, DAW launching and the containing-folder helpers read, and leaving it alone is what makes "restore to where it came from" free.
- So `isMissingFileCandidate` is `!isVirtual && !isArchived`. Anything new that reads a non-resolving path as "the file was deleted" must gate on it, exactly as version stacks already require. Getting this wrong offers to delete the one row pointing at the archive holding the work.
- `ArchiveScope` is resolved by `defaultScopeFor` in `lib/services/project_archive_service.dart`: a bundle (`.logicx`/`.luna`/`.band`) archives alone, a file with a folder to itself takes the folder, a file sharing its folder takes only itself. The shared "does anything else live here?" test is `folderIsDedicatedTo` in `lib/utils/project_folder_utils.dart`, used by moving too.
- Never let an archive land in a scan root, inside one, or above one — the next scan would re-index every zip straight back in. `conflictingScanRoot` is the guard, and it runs both at destination-pick time and again inside `archiveProject`.
- Originals are deleted only when the user asked *and* the written zip has been reopened and verified entry by entry (`verifyArchive`). Zips are written to a `.zip.part` and renamed on success, so a cancelled or crashed run never leaves something that looks finished.
- Archived state is **user data** (all three fields sync and back up); the archive *destination folder* (`archiveFolderProvider`) is a **device-local preference** and is in neither. Same split as themes.
- Archived visibility is its own 0/1/2 axis (`showArchivedProjectsProvider`), not `hidden`. Session-only, for the same reason as the hidden one.
- Archiving and moving are both refused for a **stack** — it owns no files, so doing either coherently means doing it to every member and re-pointing the stack. Members are archived and moved individually.

### A version stack is a *virtual* project — never assume a row has a file
- Version stacking (#94) makes a stack a real row in the projects box with `isVirtual: true`, whose `filePath` is the **folder** its versions live in, not a file. Anything that treats a non-resolving path as "the file was deleted" must gate on `MusicProject.isMissingFileCandidate` — `missingProjectIds` and the grid's `cloud_off` indicator already do. Getting this wrong offers to delete the one row holding a song's shared notes, todos, deadline and work time.
- A stack owns the shared metadata; its members keep their own fields **untouched but dormant**, which is what makes `unstack` lossless. Stacking promotes exactly one member's metadata (`stackProjects(metadataSourceId:)`) — nothing is ever merged, so two versions' details cannot be mangled together. The dashboard asks which member to promote only when two or more of them satisfy `MusicProject.hasUserMetadata`.
- Work time and sessions on a stack are **derived on read** (`stackTotalWorkSeconds` / `stackSessions`), never stored on the stack row. Don't add a rolled-up copy — it would need invalidating on every timer tick, member deletion and Drive restore.
- `projectsProvider` filters out stack members (`isStackMember`), so the list shows the stack instead of its versions. Anything totalling that list counts a stacked song once.
- `ScanMode.versionStack` is the third scan mode: it auto-stacks by immediate parent folder via `ProjectRepository.autoStackFolders()`, which runs after every scan. It only ever *adds* — it never unstacks, re-parents or dissolves anything, so hand-made stacks survive a rescan. Manual stacking works in **all three** modes; the mode only controls the automatic pass.

### One sound at a time: every audio player joins `AppAudioFocus`
- The app has several independent players that can be on screen together: the bottom player bar, a project's preview song, the preview dialog, a release's tracks, the playlist player, the phone player (`MobilePlayerNotifier`) and `MidiPreviewPlayer`. Each one `register`s a callback that pauses it, `claim`s the focus when it starts making sound (from its own play-state listener) and `unregister`s in `dispose` (`lib/services/app_audio_focus.dart`).
- A new player has to do the same three things, or it will play over the others. Starting a MIDI preview pausing the song underneath was the bug this fixed.
- The one deliberate exception is `MidiNoteAuditioner`: the piano roll's note-by-note feedback is a short blip over whatever plays, as in a DAW, and claiming the focus would stop the very clip being edited.

### Windows ships two installers, and one of them updates itself
- **`DAW_Project_Manager_Setup_vX.exe` (Velopack)** installs per user into `%LocalAppData%\DAWProjectManager\` (`current\`, `Update.exe`, `packages\`) and updates in place: `VelopackUpdateService` reads the release's `releases.win.json`, downloads the newest full package checked against its SHA-256, and runs `Update.exe apply`. No Velopack SDK — its update manager is .NET or Rust, and a Rust build hook would reach every platform's build, the Flatpak's offline one included. `vpk pack` runs in release.yml, beside Inno, from the same build.
- **`DAW_Project_Manager_Installer_vX.exe` (Inno Setup)** keeps its name and keeps being published: copies it installed download exactly that name from their update dialog (`windowsInstallerDownloadUrl`), so renaming it, or making it the Setup, would strand them or move them without asking. The website offers the Setup to newcomers.
- **`kVelopackPackId` must never be the data folder's name** (`daw_project_manager`): Velopack deletes `%LocalAppData%\<packId>` on uninstall, which would take the library and the DAW plugin's bridge with it. A test holds them apart and checks release.yml packs with that id.
- Velopack runs the exe with `--veloapp-install|updated|obsolete|uninstall` and kills it after 15–30 s. They are answered in `windows/runner/main.cpp` before any window exists; on uninstall it also removes the Run-key entry naming that install.
- A Setup install finding an Inno copy (`LegacyWindowsInstall`, its `_is1` uninstall entry) offers once to remove it; "Keep it" is device-local (`app_settings`).

### Launch at login: one backend per way the app is installed
- `AutoStartService` (`lib/services/auto_start_service.dart`) picks a backend in `auto_start/platform_backends.dart`: Run key (Windows `.exe`), Startup folder shortcut (MSIX — a packaged app's `HKCU` writes are private), login item/LaunchAgent (macOS, answered natively in `MainFlutterWindow.swift`), `~/.config/autostart` (Linux tarball/AppImage), the Background portal (Flatpak). The pure parts — what is written, how it reads back, what counts as stale — are in `auto_start_rules.dart` and `shell_link.dart`, and are where tests go.
- **Never register a path that moves.** The MSIX shortcut targets the execution alias (`kMsixExecutionAlias` = `msix_config.execution_alias`), never `Platform.resolvedExecutable`: the exe's folder carries the package version and every Store update deleted it, silently ending auto-start while the switch said "on". An AppImage registers `$APPIMAGE`, never its `/tmp/.mount_*`.
- Every backend reports `AutoStartStatus` through `classifyRegistration`, and `syncWithOs` rewrites a **stale** one at startup (it names this executable with the wrong form or flag, or names something gone). A registration for another install that still exists is left alone, so a dev build never takes over the release's entry. Something switched off in the OS (Task Manager, Login Items, `X-GNOME-Autostart-enabled=false`) is off and stays the user's call. Flatpak can't be asked (`unknown`), so the cached value stands.
- `--minimized` must be honoured in **three** places per platform: the registration, `main()`, and the native runner, which otherwise shows the window itself (`main.cpp`/`flutter_window.cpp`, `my_application.cc`'s first-frame callback, `MainFlutterWindow.order`). macOS doesn't pass process arguments to Dart at all; `awakeFromNib` forwards the flag.

### Launching a project in its DAW always goes through `launchProjectInDaw`
- Use `launchProjectInDaw(context, ref, project)` from `lib/ui/session_actions.dart` for every "open/launch in DAW" button — never call `FileLauncher.launchProject`/`launchWithBinary` directly from UI code.
- Why: this is the one place that knows about the DAW executable-override system (`ProjectRepository.getDawLaunchCommandPaths`, Settings > DAW Locations — every desktop platform), its missing-path remediation, and the configure prompt (`showDawLaunchCommandDialog`). A DAW type maps to a *list* of override paths: one resolves → run it, several resolve → `showDawLaunchPickerDialog` asks which. The configure prompt fires up front on Linux (no dependable OS file association) and only after a failed standard launch on Windows/macOS. A direct `FileLauncher` call bypasses all of that. The decision lives in the pure `resolveDawLaunchAction` / `shouldPromptDawLocationAfterFailedLaunch` helpers.

### Never use `ref` in `dispose()`
- Riverpod 3 refuses `ref` once a widget is unmounting: a `dispose()` that reads a provider throws every time, and the rest of it never runs. Keep the notifier in a field when the widget is set up, and change provider state after the frame (`Future.microtask`) — providers can't change while the tree is torn down. `test/ui/no_ref_in_dispose_test.dart` fails on any `ref.` inside a `dispose()` in `lib/`. Two did: the music player never handed back the bottom bar's previous/next, and a release's audio rows leaked their players and audio-focus registration.

### The screenshots are taken by code
- `scripts/capture_screenshots.ps1` runs `integration_test/screenshots/capture_test.dart`: the real app on a demo library (`DPM_DATA_DIR=daw_project_manager_screenshots`, filled by `DemoDataService`), every screen visited, `resources/screenshots/` rewritten at 1920×1080 with `DPM_HIDE_VERSION=true` (no version in the title) and `DPM_SCREENSHOTS=true` (no developer tools). A screen that can't be reached is reported and skipped.
- **A debug-only tool is gated on `showDeveloperTools`** (`lib/utils/screenshot_mode.dart`), never `kDebugMode` alone: the screenshot tool runs a debug build, and the Profile Manager's testing database buttons were in its pictures. `shot()` refuses any picture showing a label in its `_neverInAPicture` list — add a new tool's label there. It is a tool, not run by CI — and its runs found real bugs (an overflowing queue header, both `dispose()` bugs above).

### Every snackbar goes through `showAppSnackBar`
- Call `ScaffoldMessenger.of(context).showAppSnackBar(SnackBar(...))` (`lib/ui/app_snack_bar.dart`), never `showSnackBar` — `test/ui/app_snack_bar_test.dart` fails on any direct call in `lib/`.
- Why: Flutter makes a snackbar with an `action` **persist** — it never times out. "1 project hidden." with its Undo sat over the bottom of the window until the app was restarted. `showAppSnackBar` forces `persist: false`, sizes the timeout to the message (longer with an action, a caller's longer `duration` wins), adds a close button, and replaces whatever is on screen instead of queueing behind it.

### Sliders and plain-content tooltips go through `semantics_safe.dart`
- Wrap every `Slider` in `SliderOverlay`, and use `StandaloneTooltip` for a tooltip around plain content (an icon, a badge, text) — `lib/ui/widgets/semantics_safe.dart`. A button's own tooltip (`IconButton.tooltip`, a `Tooltip` around a button) needs neither. `test/ui/semantics_orphans_test.dart` fails on a bare one in `lib/`.
- Why: Flutter 3.47 sends semantics nodes no node holds — a slider's value-indicator portal in a dialog or pushed route, the second of two tooltips merged into one node, a menu anchored to something of no size — and Windows' accessibility bridge rejects the whole update ("Failed to update ui::AXTree, error: N will not be in the tree"), freezing what a screen reader sees; in a release build a later update can end the process (flutter/flutter#182444, #190357). Only with an accessibility client attached, so it looks intermittent.
- `SemanticsOrphanBinding` (`test/helpers/semantics_orphans.dart`) keeps the tree the way the engine does and records every node left out; `expectNoOrphanSemanticsWhileHovering` shows each tooltip on screen in turn. A new screen with tooltips side by side or a menu gets a test with it.

### Material comes from `material_ui`, never the SDK's bundled copy
- Import `package:material_ui/material_ui.dart` (and `cupertino_ui`), not `package:flutter/material.dart`: the SDK's design libraries are frozen since Flutter 3.44 and slated for deprecation. Same class names, different library — so the two copies' types don't mix.
- Localizations: `appLocalizationsDelegates` (`lib/utils/localization_delegates.dart`), never `AppLocalizations.localizationsDelegates` — gen-l10n still fills that with flutter_localizations' delegates, which leave material_ui widgets without `MaterialLocalizations` outside English. A test fails on any use of it.
- Dependencies still on the bundled library (trina_grid…) get the theme and localizations through `MaterialUiCompatibilityBridge` in `MaterialApp.builder`. Where a dependency's API is *typed* with bundled-Material classes (trina_grid's column menu takes `PopupMenuEntry`), import just those with `import 'package:flutter/material.dart' as sdk_material show …` — see `trina_grid_menu_delegate.dart`.

### Destructive confirm-dialog buttons need an explicit `foregroundColor`
- Any `ElevatedButton`/`FilledButton` styled with a hardcoded red `backgroundColor` (delete/remove/reset confirmations) must also set `foregroundColor` — Flutter does not derive readable text contrast from an arbitrary `backgroundColor` on its own, and the default has been wrong before.
- Pairing used throughout the app: `Colors.red` / `Colors.red.shade700` → `foregroundColor: Colors.white`; `Colors.red.shade300` (lighter, used for less-destructive actions like "Hide" or "Remove") → `foregroundColor: Colors.black`.

### A `Row` pairing a text field with a button needs `CrossAxisAlignment.center`
- `Row(children: [Expanded(child: TextField(...)), button])` defaults to `CrossAxisAlignment.start`, which top-aligns the button against the field's full decorated height (label + border) instead of visually centering it — looks broken, especially once the field grows (e.g. an `errorText`).
- Always set `crossAxisAlignment: CrossAxisAlignment.center` on this shape of `Row`. This has been the same one-line bug fixed independently in multiple dialogs — grep for `CrossAxisAlignment.start` near a `TextField` before assuming a new field+button row is fine as-is.

### A DAW logo shown as a field's `prefixIcon` needs explicit sizing
- `Image.asset(getDawLogoPath(dawType), ...)` renders at the source PNG's native size if unconstrained — oversized and breaking the field's layout when used as an `InputDecoration.prefixIcon`.
- Always pass `width: 16, height: 16, fit: BoxFit.contain`, with an `errorBuilder` falling back to `Icon(Icons.piano, color: color)` for DAWs with no logo asset. See `_buildDawPrefixIcon` in `lib/ui/project_detail_page.dart` for the canonical implementation to mirror.

### A project's visual identity is always drawn by `ProjectCoverAvatar` / `ProjectCoverBleed`
- Cover art, accent color and icon (#110) are never rendered by hand — the mobile list and the detail header use `ProjectCoverAvatar`, the projects grid uses `ProjectCoverBleed` — so the "cover art wins over color/icon" rule and the stale-path fallback live in one place.
- **Nothing is assigned by default.** `thumbnailPath`, `accentColor` and `iconKey` are all opt-in; `projectAccentColor` / `projectIcon` in `lib/utils/project_visuals.dart` return null for a project nobody has decorated, and the widgets then render *zero size*. Never invent a stand-in color, icon or placeholder image for a list row — a generic default on every row is the thing this feature deliberately does not do. `projectHasVisualIdentity` is the check for "is there anything to draw".
- The one exception is `showEmptyPlaceholder`, for editing surfaces only (detail header, appearance dialog), where the tile is the way into the editor.
- A stored `iconKey` this build no longer ships reads as "no icon", not as a crash — retiring an icon from `kProjectIconChoices` is safe.
- The grid's Name column sets `cellPadding: EdgeInsets.zero` so the bleed can reach the cell's border and span the full row height; everything else in that cell re-applies `_kNameCellInset` itself.
- In the grid, `ProjectCoverBleed` is anchored to the Name cell's **right** border and fades leftwards under the name (`_kNameCellBleedSide`); the name and its trailing badges stop before the solid square. It bleeds cover art, or — when there is none — the chosen accent colour (with its icon) at `kAccentBleedOpacity`. A project nobody decorated still draws nothing. Card covers (`ProjectCardGrid`) are masked by `cardCoverFade` so the action buttons along their foot stay visible.

### Custom fields and table columns: definitions sync, column layout does not
- A custom field (Settings > Columns & fields) is a `CustomFieldDefinition` (`lib/models/custom_field.dart`); a project's values live in `MusicProject.customFields`, keyed by the definition's **id** — renaming keeps the values. Values are stored as text even for number fields; parse with `parseCustomNumber` and sort with `compareCustomFieldValues` (`lib/utils/custom_fields.dart`), never `toString().compareTo`, or -9.8 sorts before -14.2.
- Definitions *and* values are user data (Drive + local backup). Definitions are merged by `mergeCustomFieldDefinitions` (`lib/services/custom_field_merge.dart`), shared by both. Deletion is a **tombstone** (`deletedAt` + bumped `updatedAt`), never a removal — the union merge would otherwise resurrect it. UI reads `activeCustomFieldsProvider`, which drops tombstones; only merge code should see `customFieldDefinitionsProvider`'s full list. A deleted field's values stay on the projects, dormant.
- Which built-in projects-table columns show, and their order, is `projectsTableColumnsProvider` — **device-local** (`settings` box), like the view mode. Hidden built-ins stay in the column list with `hide: true` so every row's cells still match a column; custom columns are appended after the built-ins by `arrangeTableColumns`. A grid whose column set can change must carry `encodeColumnLayout` / `customFieldColumnsSignature` in its key — Trina's columns are fixed once mounted. Each built-in also carries `inReleaseTracks`: every field (built-in or custom) can be switched on in the projects table and in release tracklists **independently**, in one shared order; `releaseTracksBuiltInColumns` is the tracklist's `visibleBuiltInColumns`. The two tables name a field the same (`dawType`, `lastModified`…) — keep it that way, or one setting stops covering both. Settings > Columns & fields draws both as a checkbox grid on striped rows (`StripedRow`).
- **Column widths are remembered per table** by `ColumnWidthMemory` (`lib/utils/column_widths.dart`): columns go through `apply` when built, the state manager is `attach`ed in `onLoaded`, and `dispose` saves what's pending. Widths are saved only after a real resize, merged (a hidden column keeps its width), under `columnWidths.<table>` in the `settings` box — **device-local**, like the column layout. With the grids' scale auto-size they act as proportions, so a layout survives a different window size. A new `TrinaGrid` should do the same three things.
- **Columns about a project that both the projects table and a release's tracklist offer** (Notes, Length, Parts) are defined once in `lib/ui/widgets/project_info_columns.dart` (`projectInfoCells` for a project's row, `emptyProjectInfoCells` for a group row). A column added to one table that would make sense in the other goes there. Users asked for exactly that: the tracklist's notes were not in the projects table, and a custom field named "Notes" is other data. New built-ins join `kProjectsTableHiddenByDefault` so an update doesn't add columns to everyone's table.
- Custom field columns are built by `customFieldTrinaColumn` (`lib/ui/widgets/custom_field_column.dart`), shared by the projects table and `ReleaseTracksTable`. The project detail page always shows every active field (`CustomFieldsEditor`); the two `showIn…` flags only add columns.
- `MusicProject.customFields` is `@HiveField(49)`, next to project stats at 48 — the two were built on parallel branches that agreed the indices up front, which is the way to avoid the duplicated-index trap above.

### The dashboard has two views and exactly one filtered list
- The desktop projects tab draws either the `TrinaGrid` table or `ProjectCardGrid` (`lib/ui/widgets/project_card_grid.dart`, #111). Both are handed the **same** `projectsProvider` output — the toggle in the filter bar chooses how that list is drawn, never what is in it. Never filter, search or re-sort inside a view; that belongs in `projectsProvider` so both views can't disagree.
- **What is in the library** (version stacks collapsed, disabled folders and stale release-preserved projects dropped) is `buildLibraryProjects` in `lib/utils/library_projects.dart`, behind `libraryProjectsProvider`. `projectsProvider` applies display filters on top of it, and the dashboard's "Projects: N (M hidden)" counts it directly. Never re-derive that set elsewhere — a hand-copied version of it is how the counts drifted from the list.
- `dashboardViewModeProvider` is a device-local preference in the `settings` box, like the theme and the detail-page layout — deliberately not Drive-synced and not backed up.
- `ProjectCardGrid` takes plain values, label strings and callbacks — no `Ref`, no Hive, no `AppLocalizations` — which is what makes it widget-testable. Resolve strings in the page and pass a `ProjectCardLabels`.
- A project with no cover art still needs a visual identity: `projectAccentColor`/`projectInitials` in `lib/utils/project_accent_color.dart` derive one from the project id, so it is identical on every machine with nothing stored. Cover art (`thumbnailPath`) wins over the generated colour, and a user-typed `MusicProject.cardInitials` wins over the derived letters (`projectCardInitials` resolves that order; blank means "go back to derived", never a blank card).
- Every card is the same size regardless of its name: the name block is a fixed two lines tall and the cover above it absorbs the difference. Anything else added to the footer has to keep that property, or one long title makes one card taller than the row.
- The card's launch / open-folder / play icons sit on the cover, not in the footer, for the same reason. The first one follows session mode — bookmark instead of launch — exactly as the grid row and the context menu do.
- Cards are ordered by `sortProjects` (`lib/utils/project_sort.dart`), shared with the mobile list's sort dropdown, driven by the device-local `dashboardCardSortProvider`. This is the *only* thing a view is allowed to do to the shared list.
- The right-click menu on a project lives in `lib/ui/project_context_menu.dart` and is shared by the grid row and the card. Add new entries there — a second copy is how the two views drift apart. Its entries come from `projectMenuChildren` (plain values in, so it's tested without Riverpod): everyday actions on top, the rest in the Files and Update details submenus, Delete last. It opens through `showAnchoredMenu` (`lib/ui/widgets/anchored_menu.dart`), a `MenuAnchor` at a point — hover submenus and the M3 animation, which `showMenu`'s flat list can't do.

### A grid row's "open full detail page" action uses `Icons.assignment` + `tooltipViewDetails`
- Every `TrinaGrid` actions column that navigates to a dedicated detail page (not an inline edit dialog) uses `Icon(Icons.assignment)` with `tooltip: l10n.tooltipViewDetails`, matching `dashboard_page.dart`'s project rows. Keep new detail-page entry points (grid action icon, row double-tap) consistent with this rather than inventing a new icon/label per page.

## Common tasks

### Cutting a release: the in-app changelog
- **Release with the `release` skill** (`.claude/skills/release/SKILL.md`), never by pushing a tag: every build uploads to a GitHub release that must already exist, so the skill creates the release (which creates the tag), checks both version gates (this changelog and the Flatpak metainfo), and retries failed runs.
- `assets/changelog/changelog.json` is the changelog the app ships — the "What's New" dialog shown once after an update, and Settings > Changelog. It is an asset, not fetched from GitHub, because the Flatpak build has no network.
- The skill writes the version's entry; by hand it is `python scripts/new_changelog_entry.py 2.10.0 --highlight "..."` (repeat `--highlight`; add `--locale pt` etc. for translations — a missing locale falls back to English). `release.yml` fails the release if the newest entry doesn't match the tag.
- Write user-facing highlights, not commit messages. Entries before 2.9.0 were backfilled from GitHub release notes and git history, and are English-only.

### Adding a new DAW
1. Add the file extension (with comment) to `ScannerService.supportedExtensions` in `lib/services/scanner_service.dart`.
2. Map the extension to a display name in `MetadataExtractor` (`lib/services/metadata_extractor.dart`).
3. Optionally add a logo asset and register it in the logo map in `dashboard_page.dart`.
4. Update the supported DAWs table in `README.md`.

### Adding a new UI string
1. Add the key + English value to `lib/l10n/app_en.arb`.
2. Add the same key to every other `app_<locale>.arb` file (use the English value as a placeholder if translation is pending).
3. Run `flutter gen-l10n` — generated code lands in `lib/generated/l10n/`.
4. Reference via `AppLocalizations.of(context)!.yourKey` — never import the generated file directly; it is re-exported from the package.

### Adding a new MusicProject field
1. Add a `@HiveField(N)` with the next available index.
2. Add a default value in the `MusicProjectAdapter.read()` for backwards compatibility with existing boxes.
3. Add the field to `copyWith()`.
4. Decide sync scope (see Non-negotiables above) and update `_serializeProject` / `_deserializeProject` if needed.
5. Update `TestFactories.makeProject()` in `test/helpers/test_factories.dart` to expose the field for tests.
